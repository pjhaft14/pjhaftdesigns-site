SugarAI · Enterprise reporting

Helping sales reps build CRM reports by asking a question in plain language.

Three sales reps did the same report task in both tools. Average time to a correct, complete answer fell from 15–18 minutes in the existing wizard to 1 minute and 20 seconds in the new builder.

The problem

A simple sales question required seven setup screens.

A sales leader might ask, “Which opportunities close this quarter, and how do they break down by sales stage?” Before the wizard showed any data, it asked for a module, filters, calculations, columns, and chart settings.

Without a preview, users had to remember earlier choices and hope the final report answered their question. Many reports ended up incomplete or abandoned because, after finishing the wizard, reps couldn’t get the data to come out the way they wanted.

The root cause was a mismatch in mental models. The wizard asked reps to think in the CRM’s structure. Reps think in business questions.

Design challenge

Make the report’s logic visible and editable.

This was one of SugarAI’s first AI features. Sales reps aren’t technical report builders, and many already used ChatGPT and similar tools. Plain language let them start from the question they already had.

But a chart can look convincing even when it includes the wrong records. I wanted reps to see how SugarAI interpreted their question and correct its filters or grouping before building the report.

Design decisions

Review the setup, edit the report, and preview changes.

01

Review before building

Considered
AI builds it with no review
Chose
A review step before anything is built

Skipping review would remove the only point where a rep can check what’s about to be built. Incorrect filters can still produce a convincing answer, and one wrong report can break trust in the feature.

02

Let people type or edit directly

Considered
A chat-only experience
Chose
A prompt and direct editing together

Experienced report builders still need precise control.

03

Preview changes before applying them

Considered
Applying refinements immediately
Chose
Preview, Undo, and version history

A short request can substantially change the answer.

The solution

A question becomes a report users can inspect.

Flow 1

Create a report from a business question

A rep can type a question or choose a suggested prompt. SugarAI checks for an existing report first.

If none fits, the rep reviews the proposed setup, corrects it, and builds the report. They can switch between the table and charts without changing the definition.

Help getting started

Suggested prompts make the first step clear.

Four prompts reflect questions from research, including pipeline by sales stage and win rate by rep.

The examples show how to specify a subject, time period, or grouping. Reps can also write their own question.

Check what already exists

Find reports that may already answer the question

SugarAI first searches existing reports and surfaces likely matches. Users can open one or start a new report anyway, avoiding duplicates without blocking creation.

Review before building

Show exactly what SugarAI is about to build

One screen brings together the data source, report type, grouping, metric, filters, and columns. Users can correct the setup before generation.

While SugarAI builds

Keep users informed while the report is being assembled

A short sequence names the work underway: reading the request, checking records, grouping the result, and preparing the chart and table.

After the report is built

Keep the report setup easy to find

The Report definition drawer keeps the setup available after the result appears, so users can inspect or refine it without starting over.

Flow 2

Refine, preview, and track history

Changing a filter used to mean leaving the report. I kept the results in view so reps could ask a follow-up and preview edits before applying them. They could undo the last change or restore an earlier version.

Why should I trust this?

Give sales teams the context to judge a report.

Before acting on a forecast, a sales leader needs to know which records it includes and whether the data is complete.

I put the applied logic, change history, and data checks in drawers so leaders can inspect an answer alongside the chart.

Results

How three reps built and revised a report.

All three completed the build and refinement tasks.

  • 01
    Average time to an answer fell from 15–18 minutes to 1 minute and 20 seconds

    In moderated calls, each rep completed the task in the existing wizard, then repeated the same task in the new builder. I timed both from the start of a report to a complete answer. The wizard had been in the product for more than 10 years, while the new builder was new to every rep, so familiarity favored the old tool. The new builder did have one advantage: reps already knew the task on their second run.

  • 02
    All three reports returned the correct records

    Each generated report pulled the right data from the system, so speed didn’t come at the cost of accuracy.

  • 03
    Two reps edited directly. One used chat.

    I kept both editing options available on the report.

  • 04
    One rep needed help finding version history

    The rep wanted to restore an earlier result but couldn’t find the control.

Retrospective

Trust came from showing the logic.

Reps trusted the result because they could see and correct SugarAI’s interpretation before anything was built. Two of the three chose direct edits over chat, which confirmed keeping both paths.

Recovery was the gap. One rep couldn’t find version history, so my next test would put a Restore action beside the edited result and check whether reps recover without prompting.

Three reps make these results directional. Before launch, I’d test with a larger group and track how often reps correct the review card, the clearest signal of whether SugarAI reads questions correctly.
